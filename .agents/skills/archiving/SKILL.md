# Archiving

开发任务完成后，将 FR 文档、Plan 文档和 git 记录整合为标准化归档文档，输出到指定目录。

> **⚠️ 核心原则：代码是唯一权威来源。**
> 所有归档文件（包括 FR 文档、Plan 文档副本）均须与实际代码保持一致。
> 任何与代码实现冲突的文档描述，必须在归档前修正，以代码为准。

## 前置检查（执行前必须确认）

归档执行前，**必须**向用户收集以下信息，缺少任何一项均不得开始归档：

| 必要信息 | 说明 |
|---------|------|
| **topic** | 归档主题名（用于目录名和文件名，使用 kebab-case） |
| **git 提交记录** | 本次任务相关的 commit hash 或 commit 范围 |
| **FR 文档路径** | 功能需求文档路径（相对或绝对路径） |
| **Plan 文档路径** | 实现计划文档路径（相对或绝对路径） |
| **归档目录**（可选） | 默认为 `docs/<topic>/archive`，用户可指定其他路径 |

若用户未提供上述必要信息，停止并逐项提示用户补充。

## 归档工作流

### Step 1：确认归档参数

```
topic:          <用户提供或从上下文推断>
archive_dir:    docs/<topic>/archive   （用户未指定时使用默认值）
fr_doc:         <用户提供的 FR 文档路径>
plan_doc:       <用户提供的 Plan 文档路径>
commits:        <用户提供的 git 提交记录>
```

向用户展示以上参数，确认后继续。

### Step 2：收集素材

依次执行以下操作，收集归档所需信息：

**2.1 读取 FR 文档与 Plan 文档**
- 读取 `fr_doc` 和 `plan_doc` 的完整内容

**2.2 获取 git 提交详情**
```bash
# 查看指定提交的变更摘要
git show --stat <commit_hash>

# 查看多个提交范围
git log --oneline <from_commit>..<to_commit>
```

**2.3 读取 git 暂存区未提交变更**
```bash
# 查看当前暂存区的所有变更
git diff --cached --stat

# 查看未暂存的工作区变更
git diff --stat
```

**2.4 读取相关核心源文件**
- 根据 git diff 输出，识别核心变更文件
- 选择性读取关键文件（不超过 5 个），用于生成准确的架构图和执行代码对齐校验

### Step 2.5：代码对齐校验（关键步骤，不可跳过）

> 以实际代码为权威，逐条比对 FR 文档和 Plan 文档，识别所有与代码实现存在偏差的描述。

**校验维度：**

| 维度 | 检查内容 | 处理方式 |
|-----|---------|---------|
| 接口 / API | 文档中的函数名、参数、返回值是否与代码一致 | 以代码为准修正文档 |
| 流程描述 | 文档中的操作流程是否与代码实际执行路径一致 | 以代码为准修正文档 |
| 数据结构 | 文档中的字段名、类型、结构是否与代码定义一致 | 以代码为准修正文档 |
| 系统模块 | 文档中提及的模块、类、服务是否实际存在于代码中 | 删除不存在的，补充遗漏的 |
| 枚举 / 常量 | 文档中的枚举值、常量名是否与代码定义一致 | 以代码为准修正文档 |
| 事件名称 | 网络事件、本地信号的名称是否与代码一致 | 以代码为准修正文档 |
| 未实现需求 | FR 中有描述但代码中未实现的功能 | 在归档文档中单独标注为"未实现" |

**输出校验报告（内部用，展示给用户，不写入归档文档）：**

```
=== 代码对齐校验报告 ===
✅ 一致项：<数量>
⚠️  偏差项：
  - [FR §2.3] 描述 "xxx" → 代码实际为 "yyy"
  - [Plan Task3] 模块 "AAA" 实际未创建，由 "BBB" 替代
  - [FR §4.1] 事件名 "OnWeaponFire" → 代码实际为 "WeaponFire"
❌ 未实现项：
  - [FR §5.2] 描述功能 "xxx"，代码中未找到对应实现
```

将校验报告展示给用户，并说明将对 FR 文档和 Plan 文档副本进行哪些修正，经用户确认后继续。

### Step 3：生成归档文档

**3.1 创建归档目录**
```bash
mkdir -p <archive_dir>
```

**3.2 复制并修正 FR 文档和 Plan 文档**

先复制原始文档到归档目录：
```bash
cp <fr_doc> <archive_dir>/
cp <plan_doc> <archive_dir>/
```

再根据 Step 2.5 的校验报告，对归档目录中的副本执行修正：
- **偏差项**：直接修改副本中的错误描述，改为与代码一致的表述
- **未实现项**：在副本对应章节末尾追加标注块：
  ```markdown
  > ⚠️ **归档注记**：本需求在当前版本未实现，代码中未找到对应实现。
  ```
- 修正完成后，在文档头部追加归档修订标记：
  ```markdown
  > 📝 **归档修订**：本文档在归档时已根据实际代码实现进行校对修正，以代码为准。修订日期：{DATE}
  ```

**3.3 生成 `<topic>.md` 归档总结**

严格按照 `templates/archive_template.md` 的结构生成归档文档，填充规则：

| 占位符 | 填充内容 |
|-------|---------|
| `{TOPIC}` | topic 名称（可读形式，如 "武器后坐力系统"） |
| `{DATE}` | 当前日期 `YYYY-MM-DD` |
| `{VERSION}` | 从 git 提交中提取，或填 `v1.0.0` |
| `{COMMITS}` | 相关 commit hash 列表 |
| `{BACKGROUND}` | 从 FR 文档提炼背景 |
| `{GOALS}` | 从 FR 文档提炼目标 |
| `{REQUIREMENTS}` | 从 FR 文档提炼核心需求列表；未实现项标注 `[未实现]` |
| 系统表格 | 从**实际代码**提炼涉及模块，不得列出代码中不存在的模块 |
| 流程章节 | 从 FR 文档提炼玩家操作流程，但须与代码执行路径对齐 |
| Mermaid 图表 | 根据实际代码生成（见图表生成规范） |
| 实现说明 | 从 Plan 文档和 git diff 提炼关键决策；记录与原始设计的偏差 |
| 文件索引 | 列出归档目录中的所有文件 |

**3.4 图表生成规范**

每张图表均使用 Mermaid 语法，**严格基于实际代码**生成，不得使用模板占位符或虚构内容：

- **类图**：覆盖本次变更涉及的核心类，包含关键属性和方法，体现继承/组合关系
- **类依赖关系图**：展示模块间 `require`/`import` 依赖链路
- **流程图**：覆盖核心功能的主路径和异常路径
- **时序图**：覆盖客户端-服务端交互的完整链路，包含关键事件名（以代码中实际事件名为准）
- **状态图**：覆盖核心对象的完整生命周期状态

可选图表（仅在任务涉及时生成）：
- 组件图：多组件协作场景
- 活动图：并发/并行逻辑场景

### Step 4：生成指导文档

**4.1 调用 creating-instruction 技能**

使用 `creating-instruction` 技能生成本次任务的开发指导文档：

**输入参数：**
- topic: `<topic>`
- 核心代码文件: 从 Step 2.4 获取的核心变更文件列表
- 架构设计信息: 从代码分析和 Mermaid 图表提取
- 开发规范要求: 从代码实现和 Step 2.5 校验报告提取
- 输出目录: `<archive_dir>/instructions/`

`creating-instruction` 需要的其他输入由 `creating-instruction` 技能直接向用户提问。

**4.2 调用 creating-autonomous-instruction 技能**（选填）

询问是否使用 `creating-autonomous-instruction` 技能生成本次任务的开发指导文档，如果需要，则：

**输入参数：**
- topic: `<topic>`
- 核心代码文件: 从 Step 2.4 获取的核心变更文件列表
- 架构设计信息: 从代码分析和 Mermaid 图表提取
- 开发规范要求: 从代码实现和 Step 2.5 校验报告提取
- 输出目录: `<archive_dir>/instructions/`

`creating-autonomous-instruction` 需要的其他输入由 `creating-autonomous-instruction` 技能直接向用户提问。

不需要该步骤则跳过

### Step 5：验证归档结果

检查归档目录内容：
```bash
ls -la <archive_dir>
```

确认以下文件均已存在：
- [ ] `<topic>.md` - 归档总结文档
- [ ] FR 文档副本（已完成代码对齐修正）
- [ ] Plan 文档副本（已完成代码对齐修正）
- [ ] `instructions/<topic>_instruction.md` - 开发指导文档
- [ ] `autonomous_instructions/<topic>_autonomous_instruction.md` - 自治开发指导文档（如果需要）

向用户报告归档完成，并列出：
1. 归档目录的完整文件列表（包含 instructions/ 目录）
2. 本次对 FR/Plan 文档执行的修正摘要（偏差项和未实现项数量）
3. 生成的指导文档说明（触发条件和主要内容概要）

## 模板位置

归档文档结构模板：`templates/archive_template.md`

创建 `<topic>.md` 时，以该模板为结构蓝图，根据实际内容替换所有 `{占位符}`。章节标题保持不变，可选章节（"可选"标注的）在内容不适用时可省略。

## 质量标准

- **代码是唯一权威**：所有描述以代码为准，文档与代码冲突时必须修正文档，不得保留冲突内容
- **Mermaid 图表**：类名、方法名、事件名必须与代码完全一致，不得使用虚构或过时的名称
- **需求描述**：忠实于 FR 文档，但经过代码对齐校验后的修正版本；未实现功能须明确标注 `[未实现]`
- **操作流程**：从**玩家/用户视角**描述，且与代码实际执行路径对齐
- **归档文档本质**：是 FR 文档 + Plan 文档经代码校验后的提炼总结，反映任务的真实完成状态
