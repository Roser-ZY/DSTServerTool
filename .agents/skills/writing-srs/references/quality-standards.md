## 1. 需求质量属性

IEEE 29148-2018 定义的高质量需求应满足以下属性：

| 属性 | 定义 | 检验方式 |
|------|------|----------|
| **完整性** | 需求描述了所有必要的条件和约束 | 是否有 TBD/TODO？前置和后置条件是否完整？ |
| **一致性** | 需求之间没有矛盾 | 不同需求描述同一行为时是否统一？ |
| **可行性** | 需求在给定约束下可实现 | 技术上是否可行？资源是否足够？ |
| **可测试性** | 需求有明确的验收标准 | 能否设计具体测试用例来验证？ |
| **可追溯性** | 需求可追溯到业务目标 | 是否能找到该需求的业务来源？ |
| **无歧义性** | 需求只有一种解读方式 | 不同读者理解是否一致？ |
| **可优先级化** | 需求有明确优先级 | 是否标注了 P0/P1/P2/P3？ |

## 2. 功能需求编写规范

### 句式规范

使用 **主语 + 情态动词 + 动词** 格式：

| 优先级 | 情态动词 | 用途 |
|--------|----------|------|
| 必须 | **shall** / **必须** | 强制性需求 |
| 应该 | **should** / **应该** | 高度推荐的需求 |
| 期望 | **may** / **可以** | 可选功能 |

**示例**:
```
✅ 正确: 系统必须在用户提交登录表单后 2 秒内返回认证结果。
❌ 错误: 系统应该比较快地处理登录。（模糊，不可测试）

✅ 正确: 系统必须对连续 5 次登录失败的账户锁定 30 分钟。
❌ 错误: 系统需要有防暴力破解机制。（不够具体）
```

### 需求粒度

- **太粗**: "系统提供用户管理功能" → 无法直接测试，需拆分
- **适中**: "管理员必须能够创建、查看、修改、禁用用户账户" → 可进一步拆分为 FR-001~FR-004
- **太细**: 描述实现细节（具体算法、代码逻辑）→ 属于设计文档内容，非需求

### 需求编号规则

```
FR-{模块代码}-{序号}

模块代码示例:
AUTH  - 认证与授权
USER  - 用户管理
ORDER - 订单管理
PAY   - 支付
NOTIF - 通知

示例: FR-AUTH-001, FR-USER-003, NFR-PERF-002
```

## 3. 非功能需求量化标准

### 性能基准参考值

| 场景类型 | 响应时间基准 | 说明 |
|----------|-------------|------|
| 简单 CRUD 查询 | < 200ms | 单表查询，无复杂计算 |
| 复杂聚合查询 | < 1s | 多表 JOIN，有索引 |
| 页面渲染（含 API）| < 2s | TTFB + 数据加载 |
| 文件上传处理 | < 5s/MB | 中等服务器配置 |
| 报表生成 | < 30s | 后台异步任务可延长 |
| 搜索接口 | < 500ms | 有搜索引擎支持 |

### 可用性等级参考

| SLA 级别 | 月停机时间上限 | 年停机时间上限 | 适用场景 |
|---------|--------------|--------------|----------|
| 99.9% (3个9) | 43.8 分钟 | 8.7 小时 | 一般业务系统 |
| 99.95% | 21.9 分钟 | 4.4 小时 | 重要业务系统 |
| 99.99% (4个9) | 4.4 分钟 | 52 分钟 | 核心交易系统 |
| 99.999% (5个9) | 26 秒 | 5.2 分钟 | 金融/医疗关键系统 |

### 安全需求基线

所有系统最低应满足的安全要求：

- **认证**: 密码最少 8 位，含大小写字母和数字；支持 MFA（高敏感度系统必须）
- **传输安全**: 全站 HTTPS，TLS 1.2+，禁用弱密码套件
- **存储安全**: 密码使用 bcrypt/Argon2 哈希（禁止 MD5/SHA1）；敏感字段加密存储
- **输入安全**: 服务端校验所有输入；参数化查询防 SQL 注入；输出编码防 XSS
- **会话安全**: JWT 有效期 ≤ 24h；敏感操作需重新认证；支持强制登出
- **审计**: 登录（成功/失败）、数据变更、权限操作必须记录日志，保留 ≥ 90 天

## 4. 需求评审检查清单

### 完整性检查

- [ ] 所有用户角色都有对应的功能需求？
- [ ] 正常流程和异常流程都有描述？
- [ ] 系统边界（包含/不包含）是否清晰？
- [ ] 非功能需求覆盖：性能、安全、可用性、可维护性？
- [ ] 所有外部接口（API、第三方系统）都已定义？
- [ ] 数据模型和字段约束是否完整？

### 质量检查

- [ ] 每条需求是否可以独立测试？
- [ ] 需求中是否有模糊词汇（快速、简单、适当、友好）？
- [ ] 需求之间是否存在矛盾？
- [ ] 需求是否描述了"做什么"而非"怎么做"？
- [ ] 优先级是否合理（P0 是否确实是 MVP 必须？）

### 可行性检查

- [ ] 性能指标在当前技术方案下可达到？
- [ ] 时间和资源约束下 P0 需求可全部实现？
- [ ] 依赖的外部系统接口已确认可用？

## 5. 常见反模式

### 模糊需求

```
❌ 反模式: "系统应该响应迅速"
✅ 正确: "系统必须在 2000ms 内响应 95% 的用户请求（基于 100 并发用户）"

❌ 反模式: "界面需要用户友好"
✅ 正确: "新用户无需培训可在 10 分钟内完成首次下单操作（基于用户测试）"

❌ 反模式: "系统需要高安全性"
✅ 正确: "系统必须通过 OWASP Top 10 安全扫描，无高危漏洞"
```

### 实现型需求（需求混入设计）

```
❌ 反模式: "使用 Redis 缓存查询结果以提升性能"（这是设计决策，非需求）
✅ 正确: "商品详情页加载时间必须 < 500ms（含首次访问）"

❌ 反模式: "使用 PostgreSQL 存储用户数据"（是约束，应放在约束章节）
✅ 正确: "系统必须支持用户数据的增删改查操作"
```

### 混合需求

```
❌ 反模式: "用户可以登录并查看订单，同时系统需要记录登录日志"
✅ 正确: 拆分为 FR-001（用户登录）、FR-002（查看订单）、NFR-S-005（登录审计日志）
```

### 假设性需求

```
❌ 反模式: "系统应支持未来可能的 API 集成"（范围不明确）
✅ 正确: 要么明确说明（支持哪个 API，交付时间），要么放入 Future Scope 章节
```
