## 1. 快速生成模式

用户提供项目描述 → AI 一次性生成完整 SRS 草稿。

### 适用场景
- 用户提供了充分的项目背景信息
- 快速原型或早期需求探索
- 用户明确要求"直接生成"

### 执行步骤

**Step 1: 解析输入**

从用户输入中提取：
- 系统名称和核心功能
- 主要用户角色
- 核心业务流程
- 已知技术约束

**Step 2: 补全缺失信息**

对于必填字段（如项目名称、核心功能），如果用户未提供，使用合理的占位符 `{待填写}` 并在文档顶部注明：

```markdown
> ⚠️ **注意**: 以下字段需补充: {字段列表}。请在评审后更新。
```

**Step 3: 按模板结构生成**

使用 `templates/srs-ieee-29148.md` 为基础，按照以下优先级填充内容：

1. 优先填充用户明确提及的内容
2. 根据业务常识补充合理默认值
3. 对不确定内容使用 `[待确认]` 标注

**Step 4: 生成后质检**

按 `references/quality-standards.md` 的检查清单快速过一遍，确保：
- 关键需求有量化指标（非"快速"/"简单"等模糊词）
- P0 需求有对应验收标准
- 有 3 条以上功能需求举例（否则提示用户补充）

**Step 5: 输出与建议**

输出完整 SRS 文档后，附上：
```
📋 建议评审重点：
1. [章节名] - {待确认的关键决策}
2. [章节名] - {需要与干系人对齐的内容}
3. 开放问题: {Q-001 等}
```

## 2. 交互引导模式

AI 分阶段提问 → 用户逐步填充 → 章节生成。

### 适用场景
- 用户需求不够清晰，需要澄清
- 用户是第一次编写 SRS，需要引导
- 复杂系统，需要深入挖掘需求
- 用户明确要求"引导我填写"

### 引导对话结构

#### Phase 1: 项目全貌（1-2 问）

```
我需要了解一下项目的基本情况：

1. 这个系统的核心目标是什么？它要解决什么业务问题？
   （例如：为电商平台用户提供订单追踪能力）

2. 主要的使用者是谁？他们的核心诉求是什么？
```

#### Phase 2: 功能范围（1-2 问）

```
基于您的描述，我初步理解系统需要：
- [总结要点1]
- [总结要点2]

请确认：
1. 哪些功能是 MVP（最小可行产品）必须包含的？
2. 哪些是第一个版本之后才考虑的？
```

#### Phase 3: 质量要求（1 问）

```
关于系统的质量要求，有几个关键指标需要确定：
- 预期同时使用的用户数量？
- 对系统可用性的要求（是否有 7×24h 需求）？
- 是否有数据安全或合规方面的特殊要求？
```

#### Phase 4: 生成与迭代

基于收集的信息，生成对应章节，然后：
```
我已生成 [章节列表]。
需要调整或补充的内容请告诉我，或者我们继续完善 [下一章节]。
```

### 引导原则

- **每次最多问 2-3 个问题**，避免让用户感到疲倦
- **先总结再提问**：每轮开始时先复述已了解的内容，再问新问题
- **提供示例选项**：如果用户不确定如何回答，提供 2-3 个参考示例
- **标记确认**：每个章节完成后明确标注 "✅ [章节名] 已完成"

## 3. 访谈问题库

### 3.1 引言章节

| 类别 | 访谈问题 |
|------|----------|
| 目的 | 这个 SRS 的主要读者是谁？（开发、测试、业务、外包？） |
| 范围 | 系统边界在哪里？哪些功能明确不在本期范围内？ |
| 术语 | 项目有哪些领域特定术语需要定义？ |

### 3.2 总体描述章节

| 类别 | 访谈问题 |
|------|----------|
| 背景 | 这是全新系统还是对现有系统的改造/扩展？ |
| 用户 | 系统有哪些类型的用户？各有什么特点和权限？ |
| 环境 | 系统部署在哪里？（公有云/私有云/混合/本地）用什么技术栈？ |
| 集成 | 需要和哪些外部系统集成？有现成接口文档吗？ |

### 3.3 功能需求章节

| 类别 | 访谈问题 |
|------|----------|
| 功能清单 | 用一句话描述系统最重要的 5 个功能是什么？ |
| 优先级 | 如果只能发布一半功能，你会保留哪些？ |
| 异常处理 | 操作失败时系统应该如何响应？需要通知谁？ |
| 历史数据 | 有无需要迁移的历史数据？量有多大？ |

### 3.4 非功能需求章节

| 类别 | 访谈问题 |
|------|----------|
| 性能 | 预计最高同时在线用户数？峰值是平时的几倍？ |
| 可用性 | 系统出现故障最长可接受的停机时间是多少？ |
| 安全 | 系统是否处理个人隐私数据？是否需要满足特定合规要求？ |
| 运维 | 谁来维护这个系统？是否有 7×24h 运维团队？ |

### 3.5 约束与假设章节

| 类别 | 访谈问题 |
|------|----------|
| 技术约束 | 有哪些不可更改的技术选型（语言、框架、数据库）？ |
| 时间约束 | 上线截止日期是什么？有哪些里程碑节点？ |
| 预算约束 | 是否有基础设施成本上限？ |
| 假设 | 你们做了哪些可能影响需求的假设？ |

## 4. 章节编写指南

### 功能需求

每条功能需求应包含：

```markdown
#### FR-XXX: {需求名称（动词短语）}

- **描述**: {系统 + 情态动词 + 具体行为}
- **优先级**: P0 / P1 / P2 / P3
- **来源**: {US-XXX / 业务规则 / 法规要求}
- **前置条件**: {必须满足的前提状态}
- **主成功场景**: {有序步骤，系统视角}
- **异常场景**: {E1: 条件 → 处理方式}
- **后置条件**: {完成后系统状态}
- **验收标准**: {Given-When-Then 或可测试的具体条件}
```

**验收标准 Given-When-Then 格式**:
```
Given（前置条件）用户已登录系统
When（操作）用户提交包含所有必填字段的订单
Then（结果）系统创建订单并返回订单号，订单状态为"待支付"，用户收到确认邮件
```

### 非功能需求

每条 NFR 必须**量化**：

```markdown
| 编号 | 指标 | 基准条件 | 目标值 | 测试方法 |
|------|------|---------|--------|----------|
| NFR-P-001 | API 响应时间 | 100 并发，P95 | < 500ms | JMeter 负载测试 |
```

禁止的写法：
- ❌ "系统应该快速响应"
- ❌ "应有较高的安全性"
- ❌ "界面需要易于使用"

## 5. 输出规范

### 文件命名

```
SRS_{项目代号}_{版本号}_{日期}.md
示例: SRS_ECOMM_v1.0_20240101.md
```

### Markdown 格式要求

- 使用标准 Markdown，兼容 GitHub / Confluence / 飞书
- 表格对齐，标题层级清晰（H1 仅文档标题，H2 为章节，H3 为子章节）
- 代码示例使用围栏代码块并标注语言
- 占位符统一使用 `{花括号}` 格式

### 版本管理建议

```
v0.1 - 初始草稿（AI 生成）
v0.2 - 作者评审修订
v0.3 - 技术评审修订
v1.0 - 首次批准发布
v1.x - 变更后小版本更新
```

### 文档状态标识

在文档顶部 `状态` 字段使用：
- `🔴 草稿` - 尚未完成，不可作为依据
- `🟡 评审中` - 等待干系人确认
- `🟢 已批准` - 可作为开发依据
- `⬛ 已废弃` - 已有更新版本替代
