# 变更影响分析策略

本文件定义从变更类型到受影响文档的映射决策树，指导 Agent 在同步时精确定位需要更新的文档。

## 变更分类

首先将变更归类到以下类型之一：

| 变更类型 | 判定依据 | 示例 |
|----------|----------|------|
| **接口变更** | 函数签名、API 端点、请求/响应结构改变 | 新增参数、修改返回类型、变更路径 |
| **行为变更** | 外部可观察的行为改变但接口不变 | 修改业务逻辑、变更错误处理策略 |
| **内部重构** | 不改变外部行为和接口 | 提取函数、重命名内部变量、优化算法 |
| **新增功能** | 新增模块、端点、功能 | 新增 API 端点、新增业务模块 |
| **删除功能** | 移除模块、端点、功能 | 弃用 API、移除功能模块 |
| **配置变更** | 环境配置、部署配置改变 | 环境变量变更、依赖版本更新 |
| **需求新增** | PRD 中新增功能需求 | 新增 FR-* 条目 |
| **需求修改** | PRD 中已有需求内容变更 | 修改 FR-* 的描述或验收标准 |
| **需求删除** | PRD 中移除功能需求 | FR-* 标记为移除 |

## 变更 → 文档影响映射

### 代码变更触发

```
接口变更
├─→ API 契约文档      [必须] 更新端点/Schema 定义
├─→ 技术设计文档      [必须] 更新详细设计中的接口描述
├─→ 测试规格文档      [必须] 更新受影响测试用例
├─→ CodeGuide        [必须] 更新函数签名和输入输出
└─→ 需求文档          [可选] 仅当接口变更反映需求理解修正时

行为变更
├─→ 技术设计文档      [必须] 更新行为描述
├─→ 测试规格文档      [必须] 更新预期结果
├─→ CodeGuide        [推荐] 更新设计意图和行为说明
├─→ API 契约文档      [可选] 仅当影响响应语义时
└─→ 需求文档          [可选] 仅当行为变更影响验收标准时

内部重构
├─→ CodeGuide        [推荐] 更新实现细节
└─→ 其他文档          [跳过] 外部行为未变，无需更新

新增功能
├─→ 技术设计文档      [必须] 新增设计章节
├─→ API 契约文档      [必须] 新增端点定义（如适用）
├─→ 测试规格文档      [必须] 新增测试用例
├─→ CodeGuide        [提示] 提示用户生成新 CodeGuide
└─→ 需求文档          [可选] 如果需求文档中未覆盖该功能

删除功能
├─→ API 契约文档      [必须] 标记端点为 deprecated
├─→ 技术设计文档      [必须] 标记对应 DM 为 deprecated
├─→ 测试规格文档      [必须] 标记对应 TC 为 SKIP
├─→ CodeGuide        [必须] 标记为 deprecated，更新索引
└─→ 需求文档          [可选] 如果需求文档中有对应条目

配置变更
├─→ 技术设计文档      [可选] 仅当影响架构或部署方案时
└─→ 其他文档          [跳过]
```

### 需求变更触发

```
需求新增
├─→ 技术设计文档      [必须] 新增 DM-FR-* 映射
├─→ API 契约文档      [可选] 如果新需求涉及新接口
├─→ 测试规格文档      [必须] 新增 TC 并更新覆盖矩阵
└─→ CodeGuide        [跳过] 代码尚未实现

需求修改
├─→ 技术设计文档      [必须] 通过 DM-FR-* 定位并更新
├─→ 测试规格文档      [必须] 通过覆盖矩阵定位并更新 TC
├─→ API 契约文档      [可选] 如果修改影响接口定义
└─→ CodeGuide        [可选] 如果修改影响已实现的设计

需求删除
├─→ 技术设计文档      [必须] DM-FR-* 标记 deprecated
├─→ 测试规格文档      [必须] 对应 TC 标记 SKIP
├─→ API 契约文档      [推荐] 对应端点标记 deprecated
└─→ CodeGuide        [推荐] 对应文档标记 deprecated
```

## 文档定位策略

### 通过编号映射定位

当文档使用编号体系时（FR-*、DM-*、TC-*、AC-*），通过编号追踪关联：

1. 从变更的代码/需求中提取相关编号
2. 在目标文档中搜索该编号
3. 定位到具体章节进行更新

### 通过关键词/路径定位

当文档无编号体系时：

1. 从变更中提取关键实体名称（函数名、类名、模块名、端点路径）
2. 在 `docs/` 目录中搜索包含该名称的文档
3. 如果存在索引文件（INDEX.md），使用索引定位

### 通过目录约定定位

按照项目文档目录结构的约定直接定位：

```
docs/
├── requirements/    → 需求文档
├── design/          → 技术设计文档
├── api/             → API 契约文档
├── test/            → 测试规格文档
├── code-guide/      → CodeGuide 文档
└── INDEX.md         → 文档索引
```

如果项目使用不同的目录结构，在首次运行时扫描并记录实际路径映射。

## 优先级排序

当多个文档需要更新时，按以下优先级顺序处理：

1. **API 契约文档** — 接口定义是其他文档的基础
2. **技术设计文档** — 设计文档指导实现和测试
3. **测试规格文档** — 测试需要与设计保持一致
4. **CodeGuide** — 代码级文档
5. **需求文档** — 通常不因代码变更而反向更新

## 冲突处理

当检测到文档间存在矛盾时：

1. 标记冲突位置和冲突内容
2. 列出可能的解决方案
3. **暂停并等待用户确认**后再继续
4. 不自行判断哪个文档是"正确的"
