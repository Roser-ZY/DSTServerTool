# Spec Doc Sync

在变更发生时保持所有规格文档和设计文档与代码/需求同步。

## 核心流程

```
变更发生 → 影响分析 → 定位文档 → 差异对比 → 同步更新 → 验证一致性
```

## 触发判定

根据触发来源确定工作模式：

**代码修改后** → 执行「代码变更同步」流程
**需求变更后** → 执行「需求变更同步」流程
**手动触发** → 执行「全量同步检查」流程
**提交前触发** → 执行「一致性审查」流程（仅报告，不自动修改）

## 前置条件

1. 读取项目文档目录结构（默认 `docs/`），确认存在哪些文档类型
2. 如果存在文档索引文件（如 `docs/INDEX.md` 或 `docs/README.md`），优先读取
3. 如果项目无已有文档，提示用户先通过对应技能生成初始文档，本技能不负责初始创建

## 文档类型与同步规则

详见 [references/doc-types.md](references/doc-types.md)，包含各类文档的结构定义和更新要点。

## 变更影响分析策略

详见 [references/sync-strategies.md](references/sync-strategies.md)，包含变更类型→影响文档的映射决策树。

## 流程一：代码变更同步

当 Agent 修改了代码时自动触发。

### 步骤

1. **变更识别**
   - 分析刚完成的代码修改：改了哪些文件、函数、类、接口
   - 使用 `git diff`（如可用）或对比修改前后内容提取变更摘要
   - 将变更分类：接口变更 / 行为变更 / 内部重构 / 新增功能 / 删除功能

2. **影响分析**
   - 根据 [references/sync-strategies.md](references/sync-strategies.md) 中的映射表，确定受影响的文档类型
   - 在 `docs/` 目录中定位具体文档文件
   - 内部重构（不改变外部行为）→ 仅更新 CodeGuide，跳过其他文档

3. **逐文档同步**
   - 按优先级处理：API 契约 → 技术设计 → 测试规格 → CodeGuide → 需求文档
   - 对每个受影响的文档：
     a. 读取当前文档内容
     b. 定位需要更新的章节（通过编号映射 FR-*/DM-* 或关键词匹配）
     c. 生成更新内容，保持文档原有风格和格式
     d. 写入更新
   - 在文档末尾或变更日志区域追加同步记录

4. **验证**
   - 检查更新后的文档内部引用是否完整
   - 确认编号映射一致性（如 FR → DM 映射未断裂）
   - 输出同步摘要

### 输出格式

```markdown
## 📋 Spec-Doc 同步报告

### 变更来源
- 文件：`src/api/auth.ts`
- 变更类型：接口变更（新增参数）

### 已同步文档
| 文档 | 路径 | 更新内容 |
|------|------|----------|
| API 契约 | docs/api/auth.yaml | 新增 `refreshToken` 参数 |
| 技术设计 | docs/design/auth.md | 更新 §3.2 认证流程 |
| 测试规格 | docs/test/auth-spec.md | 新增 TC-AUTH-015 |

### 未受影响
- 需求文档（功能范围未变）
```

## 流程二：需求变更同步

当 PRD/SRS 被修改时触发。

### 步骤

1. **变更识别**
   - 对比需求文档修改前后内容
   - 提取变更的需求条目（FR-*/NFR-*/AC-*）
   - 分类：新增需求 / 修改需求 / 删除需求 / 优先级变更 / 范围变更

2. **下游影响分析**
   - 需求新增 → 技术设计（需新增 DM 映射）+ 测试规格（需新增测试用例）+ 可能的 API 契约
   - 需求修改 → 通过编号找到关联的 DM/TC 并更新
   - 需求删除 → 标记关联文档中对应部分为 deprecated
   - 范围变更 → 更新技术设计的系统边界章节

3. **逐文档同步**
   - 按依赖顺序处理：技术设计 → API 契约 → 测试规格 → CodeGuide
   - 对每个文档执行与流程一相同的读取→定位→更新→追加记录
   - **重要**：需求删除时不直接删除下游文档内容，而是标记为 `[DEPRECATED: FR-xxx 已移除]`

4. **验证与输出**
   - 同流程一

## 流程三：全量同步检查

用户手动要求时执行。

### 步骤

1. **文档发现**
   - 扫描 `docs/` 目录下所有文档
   - 扫描代码目录中的关键接口、类、模块

2. **差异检测**
   - 对比文档中描述的接口签名与实际代码
   - 检查需求编号与设计映射的完整性
   - 检测孤立文档（无对应代码）和未文档化的代码

3. **生成差异报告**
   - 列出所有不一致项，按严重程度排序
   - 对每项不一致给出修复建议

4. **用户确认后修复**
   - 展示差异报告，等待用户确认要修复哪些项
   - 逐项修复并追加同步记录

## 流程四：一致性审查（提交前）

在 git commit 前触发，仅报告不修改。

### 步骤

1. 使用 `git diff --cached`（或当前暂存区）获取即将提交的变更
2. 分析变更是否影响任何已有文档
3. 输出审查报告：
   - ✅ 文档已同步 — 无需操作
   - ⚠️ 文档可能需要更新 — 列出建议更新的文档和原因
   - ❌ 文档明确过期 — 列出必须更新的文档

**此流程不自动修改任何文件**，仅提供建议。用户确认后可调用流程一进行同步。

## 同步记录格式

在每个被更新的文档末尾维护变更日志：

```markdown
## 变更日志

| 日期 | 变更来源 | 影响范围 | 摘要 |
|------|----------|----------|------|
| 2025-03-13 | `src/api/auth.ts` 接口变更 | §3.2 | 新增 refreshToken 参数 |
```

如果文档已有变更日志章节，在其中追加；否则在文档末尾新建。

## 重要约束

1. **最小修改原则**：只更新与变更直接相关的部分，不重写整个文档
2. **格式保持**：严格保持文档原有的 Markdown 格式、标题层级、编号体系
3. **不创建新文档**：本技能只同步已有文档，不负责初始生成
4. **不删除内容**：过期内容标记为 deprecated，不直接删除
5. **可追溯**：每次同步必须留下变更记录
6. **用户确认**：全量同步和有争议的修改需等待用户确认后执行
