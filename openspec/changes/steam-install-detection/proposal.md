# Proposal: Steam/DST 安装检测模块

## Why

当前项目正在向 Tauri 桌面应用演进，但后端还没有一套可复用的业务服务层。对于 DST 相关功能来说，"能否可靠找到 Steam、游戏本体和 Dedicated Server 的安装位置" 是很多后续能力的前置条件，例如服务器配置、模组管理、启动参数生成和健康检查。

现在仓库里缺少这个基础能力，前端也没有可调用的统一检测接口。用户需要的是一套明确、可解释、跨 Windows 与 macOS 的检测逻辑：先确认 Steam 已安装并得到安装目录，再继续定位 Don't Starve Together 与 Don't Starve Together Dedicated Server 的安装目录；若任何一层缺失，都要返回带错误码的错误信息，并给出下一步建议。同时，自动检测不能是唯一入口，用户还需要在检测失败后或检测成功后手动指定路径。

这个变更的价值不在界面层，而在于建立一层稳定的底层能力，让后续所有依赖安装路径的功能都有一致的数据来源和错误语义。

## What Changes

- 在 `src-tauri/src/` 下新增安装检测相关的服务层结构，建立第一版业务逻辑骨架
- 增加 Steam 安装检测能力，支持 Windows 与 macOS
- 在定位 Steam 根路径后，基于 `libraryfolders.vdf` 与 `appmanifest_*.acf` 检测 DST 与 DST Dedicated Server 的安装目录
- 新增统一错误码定义，覆盖 Steam、DST、Dedicated Server 以及手动路径校验场景
- 提供可被前端调用的 Tauri IPC 接口，返回检测结果、错误信息和建议操作
- 支持手动指定 Steam、DST 与 Dedicated Server 路径，并对输入路径进行独立校验

## Goals

- 为 Windows 和 macOS 提供一致的安装检测能力
- 在一个返回模型中表达成功路径、失败组件和建议操作
- 让手动指定路径成为正式入口，而不是异常兜底逻辑
- 为后续依赖安装目录的功能建立稳定接口和错误模型

## Non-Goals

- 不在本次变更中实现游戏下载、安装、修复或自动跳转安装页
- 不在本次变更中实现 Linux 检测逻辑
- 不在本次变更中完成完整前端交互界面
- 不在本次变更中处理 Steam 账号、登录状态或运行状态检测

## Scope Boundary

本次变更只处理"本机安装检测与路径校验"。判断标准是文件系统和 Steam 配置是否能证明目标组件已安装；不负责联网校验、不负责远程主机探测，也不负责启动游戏或服务器。

## Expected Outcome

变更完成后，前端或其他后端模块可以通过统一命令获取如下信息：

- Steam 是否安装，以及其安装根目录
- DST 是否安装，以及安装目录和可执行文件路径
- DST Dedicated Server 是否安装，以及安装目录和可执行文件路径
- 哪些组件缺失、对应错误码是什么、用户下一步应如何处理
- 用户手动提供的路径是否有效

这会把当前仓库从"只有 Tauri 启动入口"推进到"具备第一批可复用后端业务能力"的状态。
