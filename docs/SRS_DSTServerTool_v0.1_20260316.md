## 1. 引言

### 1.1 目的

本文档用于定义 **DSTServerTool** 的软件需求，统一产品、开发、测试对范围的理解，并为后续实现、验收和版本规划提供依据。

### 1.2 范围

**系统名称**: DSTServerTool  
**系统代号**: DSTSERVERTOOL

**系统描述**:  
DSTServerTool 是一个面向 Windows 平台《饥荒联机版》（Dont Starve Together, DST）服务器管理员的桌面工具。系统以 Tauri 为桌面容器，前端采用 Vue + Vite + shadcn/ui（其组件体系基于 Radix UI 思路与原语），提供服务器搭建引导、模组更新、存档管理、部署执行与结果追踪能力。

**本文档涵盖**:
- 基于文章所描述 DST 服务器搭建流程的可视化引导与执行
- 已完成的模组更新能力从 Python 核心向桌面应用集成的产品化需求

**本文档不涵盖**:
- Klei 官方游戏服务端本体的二次开发
- 云主机编排、远程运维平台、多用户协同后台

## 2. 总体描述

### 2.1 产品视角

DSTServerTool 是一个本地桌面运维工具，位于 DST 官方服务端、Steam 安装目录、本地存档目录与服务器管理员之间。

```text
┌─────────────────────────────────────────────────────────────────┐
│                           Windows 桌面环境                      │
│                                                                 │
│  服务器管理员 ──→ DSTServerTool ──→ Steam 安装目录              │
│                         │         ├─ steamapps/workshop         │
│                         │         └─ steamapps/common           │
│                         │
│                         ├──────→ DST Dedicated Server 目录       │
│                         ├──────→ DST 本体 mods / 存档目录        │
│                         └──────→ 本地执行日志 / 配置文件         │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 产品功能概述

| 功能模块 | 描述 | 优先级 |
|----------|------|--------|
| 搭建流程引导 | 按文章定义的流程组织服务器搭建步骤、参数录入与执行反馈 | P0 |
| 模组更新管理 | 扫描服务器模组、定位来源模组、判断更新时间并替换 | P0 |
| 部署配置管理 | 保存 Steam 路径、服务器路径、Cluster 配置与常用参数 | P0 |
| 运行结果追踪 | 展示执行日志、状态、失败原因和摘要统计 | P0 |
| 存档管理 | 导入、切换、备份、还原世界存档 | P1 |
| 启停与运维辅助 | 启动/停止服务端、执行常用维护操作 | P1 |

### 2.3 用户类别与特征

| 用户类型 | 描述 | 技术水平 | 使用频率 |
|----------|------|----------|----------|
| **服务器管理员** | 个人服或小团队服维护者，需要搭建、更新、备份服务器 | 中级 | 高频 |
| **模组维护者** | 更关注模组同步结果与异常排查 | 中级 | 中频 |
| **新手服主** | 依赖向导完成首次部署，对目录结构不熟悉 | 初级 | 低频 |

### 2.4 运行环境

| 类型 | 要求 |
|------|------|
| **目标操作系统** | Windows 10/11 64 位 |
| **桌面容器** | Tauri 2.x |
| **前端** | Vue 3 + Vite + shadcn/ui |
| **后端/本地能力** | Rust（Tauri Command）+ Python 3.x 模组更新核心兼容层 |
| **外部依赖** | 本机已安装 Steam，且存在 DST 与 DST Dedicated Server |
| **最低硬件配置** | 4 核 CPU、8GB 内存、可用磁盘空间 ≥ 10GB |

### 2.5 设计和实现约束

- **技术栈约束**: 桌面端必须采用 Tauri；前端必须采用 Vue + Vite + shadcn/ui；shadcn/ui 组件方案必须兼容其基于 Radix UI 原语的交互模式；不得继续以 React + Radix Themes 作为最终正式前端方案。
- **平台约束**: MVP 必须优先支持 Windows，本地文件系统路径与权限逻辑以 Windows 为准。
- **集成约束**: 当前已完成的 Python 模组更新逻辑必须可被桌面端复用，或以等价行为重写且通过回归验证。
- **安全约束**: 仅访问用户明确授权的本地目录；不得静默删除用户未确认的重要存档与配置。

### 2.6 假设与依赖

**假设**:
- 用户具备本机 Steam 安装权限，并已下载 DST 与 DST Dedicated Server。
- 文章中的搭建流程适合被拆解为可执行或可确认的分步向导。
- 模组更新判定仍以目录最后修改时间为准，除非后续规格另行修订。

**依赖**:
- DST 服务器搭建文章原文或可验证流程来源。
- Steam 目录结构稳定包含 `steamapps/common` 与 `steamapps/workshop`。
- Tauri 与 Python 运行环境在目标机器上可用。
- `shadcn-vue` 注册表当前未提供 `sidebar-07` block，需要以 `sidebar` 组件族做等价主布局实现。

### 2.7 当前实现基线

截至 2026-03-16，仓库内已确认完成的范围如下：

- 已存在 Tauri 桌面应用基础壳，前端已迁移为 `Vue 3 + Vite + shadcn-vue` 单页应用，并落地可折叠侧边栏主框架与占位路由页面。
- 已存在 `mods_update.py` CLI 入口和 `mods_update/core.py` 核心逻辑，可完成 Steam 路径校验、服务器模组扫描、来源模组选择、安全替换和结果输出。
- 已存在模组更新的数据模型、Quickstart 和 OpenAPI 合约草案，可作为桌面集成接口参考。

## 3. 功能需求

### 3.1 搭建流程引导

#### FR-BOOT-001 文章流程建模

- **描述**: 系统必须支持将 DST 服务器搭建文章中的流程定义为顺序步骤清单，并在界面中逐步展示。
- **优先级**: P0
- **来源**: 文章流程 + 新手服主首次搭建场景
- **前置条件**: 用户已进入“初始化部署”功能。
- **触发事件**: 用户点击“开始搭建”。
- **主成功场景**:
  1. 系统加载预置的搭建步骤模板。
  2. 系统按顺序显示步骤名称、说明、所需输入与完成条件。
  3. 用户可查看当前步骤、已完成步骤和待完成步骤。
- **异常/替代场景**:
  - **E1**: 若文章步骤模板缺失，则系统提示“流程模板未配置”并阻止开始。
- **后置条件**: 当前搭建会话被创建。
- **验收标准**: 用户可在单一界面看到完整步骤列表、当前步骤高亮和每步完成状态。

#### FR-BOOT-002 搭建参数录入

- **描述**: 系统必须在相关步骤中采集并校验 Steam 路径、DST 安装路径、Dedicated Server 路径、Cluster 配置目录等必要参数。
- **优先级**: P0
- **来源**: 首次部署流程
- **前置条件**: 当前步骤要求输入本地路径或配置项。
- **触发事件**: 用户提交参数。
- **主成功场景**:
  1. 用户选择或输入路径与配置值。
  2. 系统校验路径是否存在、目录结构是否符合要求。
  3. 系统保存通过校验的参数。
- **异常场景**:
  - **E1**: 路径不存在时，系统必须给出具体缺失位置。
  - **E2**: 目录结构不符合要求时，系统必须指出缺少的子目录。
- **后置条件**: 有效参数可用于后续步骤执行。
- **验收标准**: 对必填路径，系统能够在 1 秒内返回校验结果并给出具体错误文案。

#### FR-BOOT-003 分步执行与手动确认

- **描述**: 系统必须支持每个搭建步骤以“自动执行”或“手动完成后确认”两种方式推进。
- **优先级**: P0
- **来源**: 文章流程存在部分不可完全自动化步骤的假设
- **前置条件**: 当前步骤已展示。
- **触发事件**: 用户点击“执行步骤”或“我已完成”。
- **主成功场景**:
  1. 若步骤支持自动执行，系统调用本地命令或内部逻辑执行。
  2. 若步骤仅支持手动执行，系统展示说明、外部链接与检查项。
  3. 系统记录步骤结果、时间和备注。
- **异常场景**:
  - **E1**: 自动执行失败时，系统保留失败日志并阻止进入下一步，除非用户显式跳过。
- **后置条件**: 步骤状态更新为成功、失败、跳过或待确认。
- **验收标准**: 所有步骤都具有明确状态且支持失败重试。

### 3.2 部署配置管理

#### FR-CONF-001 配置持久化

- **描述**: 系统必须保存用户已确认的本地配置，包括 Steam 根目录、DST 游戏目录、Dedicated Server 目录、Cluster 名称和常用执行参数。
- **优先级**: P0
- **来源**: 重复运维需求
- **前置条件**: 用户已完成至少一次有效配置录入。
- **触发事件**: 用户点击保存或流程自动保存。
- **主成功场景**:
  1. 系统序列化当前配置。
  2. 系统写入本地应用配置目录。
  3. 系统下次启动时自动加载最近一次配置。
- **异常场景**:
  - **E1**: 写入失败时，系统必须提示并保留未保存状态。
- **后置条件**: 用户无需重复录入相同路径。
- **验收标准**: 关闭并重新打开应用后，最近一次保存的配置可被正确恢复。

#### FR-CONF-002 多配置切换

- **描述**: 系统应该支持保存多个服务器配置档并进行切换。
- **优先级**: P1
- **来源**: 多服务器维护场景
- **前置条件**: 至少存在一个配置档。
- **触发事件**: 用户创建、重命名或切换配置档。
- **主成功场景**:
  1. 用户新建配置档并录入参数。
  2. 系统保存并列出所有配置档。
  3. 用户切换后，界面刷新为对应配置。
- **异常场景**:
  - **E1**: 新配置名称重复时，系统拒绝保存并提示重名。
- **后置条件**: 当前活动配置明确。
- **验收标准**: 系统可稳定维护不少于 10 个本地配置档。

### 3.3 模组更新管理

#### FR-MOD-001 Steam 目录发现

- **描述**: 系统必须允许用户指定 Steam 根目录，并基于该目录定位 `steamapps/common` 与 `steamapps/workshop`。
- **优先级**: P0
- **来源**: 已实现 Python 模组更新能力
- **前置条件**: 用户准备执行模组更新。
- **触发事件**: 用户点击“扫描模组”或“执行更新”。
- **主成功场景**:
  1. 用户输入或选择 Steam 根目录。
  2. 系统校验 `steamapps` 结构。
  3. 系统定位 DST 与 Dedicated Server 目录。
- **异常场景**:
  - **E1**: Steam 根目录不存在时，系统提示无效路径。
  - **E2**: 缺少 `steamapps/common` 或 `steamapps/workshop` 时，系统提示目录不完整。
- **后置条件**: 模组扫描上下文已建立。
- **验收标准**: 无效路径不会触发后续扫描逻辑。

#### FR-MOD-002 服务器模组扫描

- **描述**: 系统必须扫描 Dedicated Server `mods` 目录下所有 `workshop-<id>` 目录并记录编号与更新时间。
- **优先级**: P0
- **来源**: `mods_update/core.py`
- **前置条件**: Dedicated Server `mods` 目录存在。
- **触发事件**: 模组更新流程开始。
- **主成功场景**:
  1. 系统遍历服务器 `mods` 目录。
  2. 系统识别合法的 `workshop-<id>` 目录。
  3. 系统收集模组编号、路径和最后修改时间。
- **异常场景**:
  - **E1**: 目录不可读时，系统记录失败原因并终止本次扫描。
- **后置条件**: 服务器模组列表可供后续比对。
- **验收标准**: 非 `workshop-` 前缀目录不会被纳入更新目标。

#### FR-MOD-003 来源模组匹配与优选

- **描述**: 系统必须在 `steamapps/workshop` 和 DST 游戏 `mods` 目录中查找匹配模组，并在存在多个来源时选择更新时间最新的目录。
- **优先级**: P0
- **来源**: 已实现 research/spec 决策
- **前置条件**: 已获得服务器模组编号列表。
- **触发事件**: 来源扫描开始。
- **主成功场景**:
  1. 系统在两个来源目录中查找同编号目录。
  2. 系统收集所有候选来源。
  3. 系统按最后修改时间选择最优来源。
- **异常场景**:
  - **E1**: 未找到匹配来源时，系统将该模组标记为 `missing`。
- **后置条件**: 每个服务器模组都获得最优来源或缺失状态。
- **验收标准**: 当两个来源均存在时，系统选择最后修改时间较新的目录。

#### FR-MOD-004 安全替换

- **描述**: 系统必须仅在来源模组更新更晚时替换服务器模组目录，并在替换失败时回滚到原状态。
- **优先级**: P0
- **来源**: `safe_replace_dir` 实现
- **前置条件**: 已找到来源模组。
- **触发事件**: 系统确认来源更新时间大于服务器模组更新时间。
- **主成功场景**:
  1. 系统复制来源目录到临时目录。
  2. 系统备份现有服务器模组目录。
  3. 系统完成替换并清理临时备份。
- **异常场景**:
  - **E1**: 拷贝或重命名失败时，系统恢复原目录并记录失败原因。
- **后置条件**: 服务器模组要么成功更新，要么保持原状态。
- **验收标准**: 任一单模组替换失败后，目标目录不得处于半更新状态。

#### FR-MOD-005 结果展示与摘要

- **描述**: 系统必须展示每个模组的处理状态、原因、来源路径、目标路径，并提供 `updated`、`unchanged`、`missing`、`failed` 四类统计摘要。
- **优先级**: P0
- **来源**: `mods_update.py` 当前输出行为
- **前置条件**: 模组更新流程完成。
- **触发事件**: 结果生成。
- **主成功场景**:
  1. 系统生成逐项结果列表。
  2. 系统生成统计摘要。
  3. 用户可查看失败原因并重新执行。
- **异常场景**:
  - **E1**: 若未发现任何服务器模组，系统显示空结果提示而非报错。
- **后置条件**: 用户可追溯本次更新执行结果。
- **验收标准**: 100% 被处理的模组都有明确状态和值得操作的原因说明。

### 3.4 存档管理

#### FR-SAVE-001 存档导入

- **描述**: 系统应该支持导入现有 DST Cluster 存档目录，并校验其基本结构。
- **优先级**: P1
- **来源**: 当前原型界面“导入现有存档”
- **前置条件**: 用户提供存档目录。
- **触发事件**: 用户点击“导入现有存档”。
- **主成功场景**:
  1. 用户选择本地 Cluster 目录。
  2. 系统校验目录结构。
  3. 系统登记为可管理存档。
- **异常场景**:
  - **E1**: 缺少关键配置文件时，系统提示并拒绝导入。
- **后置条件**: 存档进入可管理列表。
- **验收标准**: 导入后用户可在列表中看到名称、路径、最近修改时间。

#### FR-SAVE-002 存档备份与恢复

- **描述**: 系统应该支持对选定存档执行本地备份与恢复。
- **优先级**: P1
- **来源**: 原型界面能力方向
- **前置条件**: 已导入至少一个存档。
- **触发事件**: 用户点击备份或恢复。
- **主成功场景**:
  1. 系统创建带时间戳的备份目录。
  2. 系统记录备份元数据。
  3. 恢复时系统提示确认并替换目标存档。
- **异常场景**:
  - **E1**: 磁盘空间不足时，系统阻止备份并提示。
- **后置条件**: 可追溯的备份点被创建或恢复完成。
- **验收标准**: 用户可恢复到任一有效备份点，且恢复后目录内容与备份一致。

### 3.5 运行结果追踪

#### FR-OPS-001 执行日志

- **描述**: 系统必须记录部署、模组更新、存档操作等本地任务的开始时间、结束时间、状态和详细日志。
- **优先级**: P0
- **来源**: 运维可追溯需求
- **前置条件**: 任一任务被触发。
- **触发事件**: 任务执行。
- **主成功场景**:
  1. 系统创建任务记录。
  2. 系统持续写入过程日志。
  3. 任务完成后写入结果摘要。
- **异常场景**:
  - **E1**: 任务崩溃时，系统仍需保留已有日志。
- **后置条件**: 用户可复查任务历史。
- **验收标准**: 最近 100 次任务执行记录可被查询和查看。

#### FR-OPS-002 失败定位辅助

- **描述**: 系统应该将失败原因映射为可操作提示，例如缺失目录、权限不足、路径错误、文件占用。
- **优先级**: P1
- **来源**: 异常排查需求
- **前置条件**: 任务结果为失败。
- **触发事件**: 用户打开失败记录。
- **主成功场景**:
  1. 系统提取失败类型。
  2. 系统展示原始错误与建议操作。
  3. 用户可直接重试或跳转到相关配置页。
- **异常场景**:
  - **E1**: 未识别错误类型时，系统至少展示原始错误文本。
- **后置条件**: 用户可继续排查或修复配置。
- **验收标准**: 对常见本地路径/权限错误，系统提供针对性提示。

### 7.1 UI 需求

- 系统必须提供桌面主导航，至少包含“初始化部署”“模组更新”“存档管理”“任务记录”“设置”。

## 8. 系统约束与假设

### 8.1 业务约束

- MVP 以单机本地运维为目标，不包含远程服务器面板能力。
- 模组更新仅处理服务器 `mods` 目录中已经存在的 `workshop-<id>` 目录，不自动新增未知模组。

### 8.2 技术约束

- 正式前端必须维持 `Tauri + Vue + Vite + shadcn-vue` 方案，并复用其基于 Radix Vue/Reka UI 原语的组件体系。
- 现有 Python 模组更新行为是必须保持的兼容基线。
- 路径、权限、文件锁定等异常必须按 Windows 行为优先处理。

### 8.3 风险矩阵

| 风险编号 | 风险描述 | 影响 | 缓解措施 |
|----------|----------|------|----------|
| R-001 | 未拿到文章原文导致搭建步骤不完整 | 高 | 将步骤标记为待核对，并在评审时补齐原文映射 |
| R-002 | Python 与 Tauri 集成复杂度高 | 中 | 保留 CLI 兼容层，先做子进程集成 |
| R-003 | 用户目录权限或文件占用导致更新失败 | 高 | 做好预检查、回滚和错误提示 |
| R-004 | `shadcn-vue` 注册表缺少部分 React block 模板，导致 UI 复刻需手工组装 | 中 | 以官方 `sidebar` 等组件族为基础做等价实现，并将布局骨架独立为可复用壳层 |
